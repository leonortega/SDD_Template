# .template/scaffold — starting shapes for generated apps

The template ships **no product code** (ADR-0005): `apps/` is empty and every
`apps/<appId>/` folder is generated by the AI scaffold
(`dev-flow-scaffold-project`) + `scaffold-k8s` after a stack is selected.

The files in this directory are the **starting shapes** the scaffold copies and
adapts — they are never deployed directly and are not registered in
`apps.json`/`ports.json`:

| Path                          | What it is                                                        |
| ----------------------------- | ----------------------------------------------------------------- |
| `apps/service/`               | Deployable app shape: Deployment + Service (+ per-app kustomization) |
| `apps/job/`                   | Wait-for-completion Job shape (no Service, no ports — ADR-0003)    |
| `db-bootstrap/`               | Engine-level bootstrap (logical DBs/roles/extensions) — the script + engine-client image the scaffold rewrites per selected engine |
| `packages/node/`              | Shared-library skeleton (package.json, tsconfig, src stub, unit test) — materialized as `packages/<pkg>/` with `<pkgName>` substituted for JS/TS stacks |

Placeholder conventions:

- `<appId>` is the app identifier from `apps.json` (lowercase, `^[a-z][a-z0-9_-]*$`).
- `<pkgName>` is a shared-library name in `packages/` (lowercase, `^[a-z][a-z0-9_-]*$`).
- Ports: the role's `containerPort` fallback from `infra/deployment/roles.json`;
  per-env nodePorts come from `assign-app-ports` → `ports.json`.
- Stack-specific artifacts (Dockerfile, package manifests, test config) are
  generated per stack — never from a fixed template list.

## Lifecycle: packages shapes are NOT pruned

The `packages/` shapes stay — unlike app shapes, they are not tied to a
registered appId, so `prune-scaffold` never removes them. Once a real
implementation of a package exists, delete its shape by hand if you want the
shape list to shrink.

## Lifecycle: shapes are pruned once implemented

A shape is a **starting point**, not a permanent template. Once a real app of its
kind is registered in `apps.json` (implementation complete), the shape is
redundant — the real app is the reference. Run:

```bash
python -m tools.sdd_cli environment-lab prune-scaffold
```

It removes, per registered app kind:

- `apps/service/` — when any `kind: service` app is registered
- `apps/job/` — when any `kind: job` app is registered
- `db-bootstrap/` — when the `db-bootstrap` app itself is registered

`dev-flow-implement-ticket` runs this as step 9.5 after implementation. Use
`--dry-run true` to preview. The empty template (no apps registered) keeps all
shapes; a converged template ends with only real implementations.

Note: the generic `apps/job/` shape is pruned as soon as **any** job-kind app is
registered — including `db-bootstrap`. If you plan additional job-kind apps
(e.g. per-app migration jobs), register them in `apps.json` before (or in the
same change as) `db-bootstrap`, or the generic job shape will be gone before
they can be scaffolded from it.
