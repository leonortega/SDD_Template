# ADR-0005: No Reference Apps In The Template

## Status

Accepted (2026-08-12). Decision driven by the human owner: the template must ship no product code and no fake
product names — "no implementations in the template; all the code will be generated by the agent in the scaffold
step; keep the files you need in `.template/` as templates." Drafted by the AI at the owner's request; the human
owner retains final say.

## Context

ADR-0002 established `apps/<appId>/` + `packages/` as the product layout, and the template shipped two **reference
apps** (`web-storefront`, `api-orders`) plus `db-bootstrap` under `apps/` so the overlay composition, port
allocation, health probe, and CI phased-apply could prove themselves against concrete shapes. They were registered
in `ports.json` and composed into every env overlay.

The owner's feedback: the template kept surfacing these fake product names everywhere (`apps/`, `ports.json`,
`kind-config.yaml`, `service-patch.yaml`, the health probe, docs). This is a template — product code is generated
by the AI scaffold after a stack is chosen, and anything the template itself needs as a starting point belongs in
`.template/`, not `apps/`.

## Decision

The shipped template contains **no reference apps**:

- **`apps/` ships empty** (README only). No reference shapes, no fake product names.
- **`ports.json` ships without per-app entries** — `appPorts: {}` and empty env blocks. The port *scheme* lives in
  `infra/deployment/roles.json` (ADR-0004); `load_ports` accepts empty assignments, `kind-config.yaml` renders no
  `extraPortMappings`, and no `service-patch.yaml` files are written until apps exist.
- **Env overlays compose only `infra/k8s/shared/database/`** (the shared-engine machinery stays in `infra/`).
- **Starting shapes move to `.template/scaffold/`** as templates the scaffold materializes: `apps/service/`
  (Deployment + Service), `apps/job/` (wait-for-completion Job), and `db-bootstrap/` (engine-client image +
  idempotent bootstrap script). Each shape has a **prune point**: once a real app of its kind is registered in
  `apps.json` (implementation complete), the shape is deleted by `prune-scaffold` (Section: Scaffold shape
  lifecycle) — the real app becomes the reference, and the template never carries starter shapes alongside
  implementations.
- **Health probe fallback defaults trimmed to the shared database only** — the standalone fallback carries just the
  shared engine's per-env ports (ADR-0003); app services appear from the mounted `ports.json` once apps are
  registered.
- **CI URL-discovery fallback app list removed** (was a hardcoded `web-storefront` entry when `apps.json` is
  missing — now an empty list).
- **Legacy appId→role fallbacks removed** from `k8s_ports.py` (`_LEGACY_APP_ID_ROLES`, the `kind_config_yaml`
  role-label map) — dead code once no reference apps ship; `ports.schema.json` already requires an explicit `role`.

Deliberately **not** changed:

- `infra/k8s/shared/database/` (StatefulSet + PVC + `db`, ClusterIP base upgraded to NodePort per env via
  the overlay service patches from `ports.json`) stays — it is the template's deployment machinery (ADR-0003), not
  product implementation.
- Test fixtures keep arbitrary appIds (`app-web`/`app-api`) — the machinery is proven by the test suite, not by
  shipped shapes.
- Historical ADR text and `knowledge/` lessons may still mention the old example names as illustrations of past
  decisions; they are not live references.

## Consequences

- The consumer no longer sees fake product names in the shipped template: `apps/` is empty, `ports.json` has no
  per-app entries, and `kind-config.yaml`/`service-patch.yaml` carry nothing until apps are registered.
- The consumer flow is: pick a stack → `dev-flow-scaffold-project` + `scaffold-k8s` generate `apps/<appId>/` from
  `.template/scaffold/` → register apps in `apps.json` → `assign-app-ports` fills `ports.json` → overlays,
  `kind-config.yaml`, the health probe, and CI pick the apps up automatically.
- **Scaffold shape lifecycle:** each implemented kind prunes its shape. `environment-lab prune-scaffold` reads
  `apps.json` and deletes `.template/scaffold/apps/service/` (when any `kind: service` app is registered),
  `.template/scaffold/apps/job/` (any `kind: job` app), and `.template/scaffold/db-bootstrap/` (when the
  `db-bootstrap` app itself is registered). `dev-flow-implement-ticket` runs it as step 9.5 once implementation
  is registered and checks pass, so a shipped template converges to real implementations only.
- All gates stay green in the empty template: overlays render the shared database, `validate-app-config` passes
  with `"apps": []`, and the port/overlay drift guards pass with no mappings.
- ADR-0003's `db-bootstrap` ships as a scaffold template (`.template/scaffold/db-bootstrap/`), not a live
  reference shape; it is materialized on registration.
