## Context

The repository is a product-free SDLC shell: the delivery harness (`docs/`, `infra/`, `.agents/`,
`knowledge/`, `openspec/`, `.gitea/`, `tools/`) lives at the root and no product tree exists yet.
The shell currently scaffolds a root `src/` + `test/` skeleton, which suits a single deployable unit
but not the intended portfolio of **twelve deployable applications**.

The deployment machinery already assumes multi-app operation:

- `infra/deployment/apps.json` maps every deployable app to a `projectPath` (Docker build context),
  a role (web/api), a health path, and a deploy order.
- `.gitea/workflows/package-deploy.yml` is a single pipeline: resolve SHA → deployable-changes gate
  (src/test diff) → build + push images to Nexus :5001 → load into kind → Kustomize apply per
  environment → health gate → discover URLs → upload evidence files to Nexus :8088.
- Kustomize overlays are environment-centric (`infra/k8s/overlays/{dev,qa,prod}`) and patch all apps
  at once; nodePorts are cluster-scoped per environment (`infra/deployment/ports.json`).
- Nexus is the artifact source of truth: :5001 stores immutable `{appId}:{commitSha}` images, :8088
  stores the evidence trail (`container-images.json`, `deployable-apps.json`, `release-{env}.json`,
  `env-urls-{env}.json`) consumed by the delivery agents. PROD reuses the QA-approved images and
  never rebuilds.

Decisions reached in design discussion with the human owner:

- A self-contained folder per deployable app, named `apps/` (not a root `src/` + `test/` pair).
- Shared code across the twelve apps lives in a `packages/` sibling.
- Per-app Kubernetes manifests live in `apps/<appId>/deploy/` and are **composed into the environment
  overlays**, keeping one Kustomize apply per environment.
- Keep the current Nexus evidence model (Docker registry + raw evidence files).
- Kubernetes is the **only** deployment target; the product is never deployed from a local machine.

## Decision

Adopt the following repository layout for all product code:

```text
apps/                      # Deployable applications (one folder per app)
  <appId>/                   # generated by the scaffold — never shipped (ADR-0005)
    src/                   # Application source
    test/                  # unit/, integration/, e2e/, architecture/
    migrations/            # per-app schema migrations slot (ADR-0003); tool implied by resolved stack
    deploy/                # Per-app Kubernetes manifests (Deployment+Service, or Job for kind: job)
    Dockerfile
    .dockerignore
    app.json               # appId, role, kind, healthPath, templateVersion marker
packages/                  # Shared libraries consumed by apps (auth, UI kit, API client, domain)
```

Package skeletons are scaffold-generated per stack: `scaffold_project_files`
materializes `.template/scaffold/packages/<runtime>/` into `packages/<pkg>/`
(substituting `<pkgName>`), and the template itself ships `packages/` empty
(ADR-0005).

See `ADR-0003` for the extension of this layout with a shared database engine
(`infra/k8s/shared/database/`), the `kind: service|job` app classification, and the phased
CI apply order (Jobs before Deployments).

Deployment model:

1. **App ownership** — each app owns its source, tests, Dockerfile, and `deploy/` manifests. The
   Docker build context is `apps/<appId>/`, set via `apps.json → projectPath`.
2. **Composed overlays** — `infra/k8s/overlays/{dev,qa,prod}` remain the single Kustomize entry
   point per environment and reference each app's `apps/<appId>/deploy` kustomization via relative
   paths (`../../../../apps/<appId>/deploy` — four levels up from `overlays/{env}/`). The env
   `service-patch.yaml` stays wired under `patches:` (strategic merge against the app Service, not
   a second resource). CI keeps one `kustomize build`/apply per environment.
3. **Cluster-level concerns stay in `infra/`** — namespaces, kind configuration, port allocation
   (`ports.json`, `service-patch.yaml`), and shared cluster resources.
4. **Single pipeline with app mapping** — `package-deploy.yml` stays one workflow. On PR-merge
   auto-deploys, the changed-path diff maps to the affected `apps/<appId>/` and only those apps are
   built/deployed. Shared-code changes under `packages/**` must map to their dependent apps —
   per-app workflow `paths:` filters would trigger **no** workflow for a `packages/**` change and are
   therefore not used. `workflow_dispatch` promotion (QA/PROD) remains unconditional and deploys
   all apps of the pinned commit (PROD artifact-reuse contract).
5. **Nexus evidence model retained** — the :5001 registry holds immutable images; :8088 holds the
   evidence files. PROD verifies `container-images.json` + registry image existence before promoting
   the QA-approved commit.
6. **No local deploys** — the product is only deployed by CI into Kubernetes. Local machines run the
   lab harness (`infra/compose.yml`) and pre-push validation (`stack-tests`) only.
7. **Template versioning without Copier** — each app records its generation source in
   `apps/<appId>/app.json` (`templateVersion`); Copier is not introduced.
8. **Guardrails** — a lefthook pre-commit hook fails staged commits whose `apps/**` diff contains
   template placeholder tokens (e.g. `{{`, `__APPNAME__`), catching a bad scaffold merge before it
   reaches Gitea CI. Static scanners (`bandit`, `checkov`, `gitleaks`, `semgrep`) run under Trunk
   locally (lefthook → `trunk check`) and in CI (`pr-validation.yml`); product paths
   (`apps/**`, `packages/**`) are checked by default, and `.template/**` is excluded by adding it to
   `.trunk/trunk.yaml → lint.ignore` (generator/reference content only, never scanned). Scanner
   rulesets stay at the root: `.semgrep.yml` holds `rules: []` and the active rule set ships as
   `.semgrep-rules.json` (read by CI). gitleaks path suppressions belong in
   `.gitleaks.toml [allowlist]` — **not** `.gitleaksignore`, which accepts full fingerprints only —
   and a `^\\.template/` allowlist entry is added for future example secrets. The only placeholder
   secrets present today are `infra/deployment/configuration.json` (`your-db-password`,
   `your-email-password`), already covered by the `CKV_SECRET_6` skip in `.checkov.yml`.

## Consequences

Positive:

- One folder per deployable unit makes Docker/CI scoping clean for twelve apps and keeps each app
  independently buildable, testable, and deployable.
- Composed overlays preserve the existing single-apply-per-environment deploy flow and the nodePort
  validation model.
- The deployable-changes gate (`(^|/)(src|test)/` at any depth) already matches
  `apps/<appId>/src/...` — no change required.
- `validate_app_config` (the `{projectPath}/Dockerfile` check) works as-is once `projectPath`
  points at `apps/<appId>`.
- A shared `packages/` prevents duplication of cross-app concerns (auth, UI kit, API client).

Required changes:

- `scaffold_project_files()` must create the `apps/` container (plus one layout app named from the
  project name recorded by `set-project-stack`) instead of a root `src/` + `test/` skeleton.
- `stack_tests.py` package-root discovery patterns must add `apps/*/` (and `apps/*/src/` for
  colocated lockfiles).
- LANDED: `infra/k8s/base/` per-app manifests migrated into `apps/<appId>/deploy/` (per-app
  `kustomization.yaml` + `{app}-deployment.yaml` + `{app}-service.yaml`), env overlays compose
  them via relative refs, and `scaffold-k8s` generates that shape. NodePort validation stays
  intact: the rendered-overlay gate (`validate-k8s-overlays`) and the CI `service-patch.yaml`
  cross-check both operate unchanged. Per-app Services carry the dev nodePort baked in, overridden
  per env by the service patch (both unwired-patch failure modes are still caught — drift for
  qa/prod, missing for all envs). Known follow-up: `scaffold-k8s` only generates an overlay
  `kustomization.yaml` when missing, so adding an app to `apps.json` requires manually adding its
  `deploy/` ref to existing committed overlays.
- LANDED: the workflow build/deploy steps are app-aware — on PR-merge auto-deploys only the gate's
  `AFFECTED_APPS` are built, image-tagged, applied (manifest filtered to those resources), and
  rollout-waited; `packages/**` changes resolve to dependent apps via each app's optional
  `dependsOn` list in `apps.json` (no dependents → not deployable); unconditional dispatch
  (pinned QA/PROD promotion, fails-open runs) passes `AFFECTED_APPS=ALL` and keeps the
  pre-filter all-apps behavior. Nexus metadata (`deployable-apps.json`, `container-images.json`)
  lists the same subset so evidence matches what was deployed; QA's unconditional re-run
  overwrites it with the full app set PROD verifies.
- `.trunk/trunk.yaml` `lint.ignore` gains `.template/**` (the four scanners skip it at once).
- `.gitleaks.toml` `[allowlist]` gains a `^\\.template/` path entry; `.gitleaksignore` stays
  fingerprint-only.
- `.gitignore` — the `!src/backend/Data/` + `!src/backend/Data/**` negations are layout-specific
  (case-insensitive ignore can silently drop source, knowledge-coverage §12a) and must be
  re-pointed at the EF Core Data layer under its app folder.
- Docs referencing root `src/`/`test/` must be updated: `docs/architecture/deployment.md`,
  `docs/architecture/system.md`, `knowledge/references/project-map.md`, plus the `src/` + `test/`
  scaffold rule in `dev-flow-implement-ticket/SKILL.md`, the `src/backend/Data/` and
  `frontend/src/...` examples in `dev-ops-configure-k8s/SKILL.md` and
  `configure-ci-workflows/SKILL.md`, and the single-`test/` rule in `test-requirements.md`
  (one `test/` per app).
- Cross-app shared code introduces package dependency wiring that the single-app shell did not have.
